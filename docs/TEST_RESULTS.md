## Windows 手工验证

1. 等待旧任务结束，覆盖 `extension`、`native-host` 及根目录 `register.ps1`，保留原运行环境；Chrome 扩展重新加载。仅首次使用或移动程序目录后需重新注册。
2. 设置页显示已连接，已有目录、勾选项自动恢复；修改保存后关闭再开，确认仍在。先确认连接，再检测 BitComet，区分安装路径与磁力关联。分别选择标准/窄版保存，确认下次打开大小正确，重启 Chrome 后仍保留样式。
   重开固定菜单，确认不再缩成只剩设置、底部按钮可见，中间内容可滚动；Chrome 内按 Alt+Shift+Y，若未触发则到 chrome://extensions/shortcuts 确认实际分配。
3. 选取此前未采集的新帖子，确认新目录无摘要；旧目录复用不是新建命名验证。
4. 在浏览器中确认原图可打开，点击采集并允许访问实际图片站点。核对两张图片可正常打开、任务没有图片失败事件。
5. 重复采集，确认不重复取完整图片；删除一张测试图片后点击检查缺失文件，仅补齐该图。
6. 取图过程中取消，确认不继续提交磁力；如失败，保留插件错误文字或对应日志继续诊断。
7. 最后测试 Chrome 与 BitComet 联动，手工确认任务保存位置。

旧版测试和使用记录单独保留在 `LEGACY_TEST_RESULTS.md`、`legacy-test-results.json` 和 `LEGACY_README.md`。

## TLS 回归（9 项，包含在 54 项内）

通过 OpenSSL CLI 在临时目录生成测试 CA、服务器证书和临时私钥，采用 Python MemoryBIO 完成实际 TLS 握手，不连接外网。默认信任库拒绝未知测试 CA，并复现 verify_code=20 及 CERTIFICATE_VERIFY_FAILED；加载正确测试 CA 后握手成功；错误域名和过期证书仍被拒绝。临时私钥在测试后删除，不纳入源码或交付包。

另检查公共 CA 的来源 SHA-256、资源缺失/无效时拒绝使用、证书与主机名验证保持开启、TLS 失败时关闭连接且不发送 HTTP 请求，以及证书失败不会重复进行无效下载尝试。

公共 CA 资源来自原包中已校验的 certifi 2026.10.19，包含 120 个 CA；不改变 Windows 证书存储或浏览器安全设置。Windows 实际信任库、服务器证书链及用户网络代理仍需实测。
